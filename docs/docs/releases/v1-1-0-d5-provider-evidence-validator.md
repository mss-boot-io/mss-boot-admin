# D5 Provider evidence validator checkpoint

This page records the untagged `v1.1.0` development checkpoint at
`668dfe3b92fdf4c01e214b38112fafeeb4ef4d91`. It adds the machine boundary that
will validate a provider maturity artifact at feature freeze. It does not create
that artifact, start a provider, contact a provider endpoint, or promote a provider.

## Implemented contract

The checkpoint adds:

- `.mss/schemas/provider-maturity.schema.json`, the strict source schema for a
  `ProviderMaturityReport`;
- `internal/mss/provider`, which loads only slash-separated repository-relative
  JSON, rejects unknown fields and repository escape, validates semantic identity
  and result counts, sorts rows deterministically, and evaluates required evidence;
- `mss provider evidence`, with text or JSON output and an optional `--required`
  gate. A negative JSON report is written before the command returns its non-zero
  result so release automation can retain the diagnosis.

Every source report pins a semantic release version, a full lowercase commit SHA,
and a unique provider/capability/fixture identity. Result counts must be internally
consistent. Under `--required`, an empty required selection, zero-run result, skip,
failure, partial pass, or cached-only result fails. Optional rows remain visible but
cannot fail the required gate.

The normalized output omits timestamps, so identical source evidence produces
identical JSON. This determinism applies to validation output only; it is not a claim
that any fixture or external deployment has been exercised.

## Exact development evidence

The implementation commit was checked with one uncached race-enabled run of exactly
the six new validator tests and three new CLI tests:

```shell
go test -race -count=1 ./internal/mss/provider \
  -run '^(TestLoadProviderEvidenceAcceptsStrictPinnedReport|TestLoadProviderEvidenceRejectsInvalidIdentityAndUnknownFields|TestEvaluateRequiredProviderEvidenceAcceptsFreshQualifiedFixtures|TestEvaluateRequiredProviderEvidenceRejectsZeroHitSkipAndCachedOnly|TestEvaluateOptionalProviderEvidenceDoesNotBlockRequiredGate|TestProviderEvidenceReportJSONIsDeterministic)$'

go test -race -count=1 ./internal/mss/app \
  -run '^(TestRootRegistersProviderEvidenceHelp|TestProviderEvidenceCommandPassesRequiredAndWritesJSON|TestProviderEvidenceCommandWritesNegativeReportBeforeReturningError)$'
```

Both packages passed. No RustFS container, S3-compatible service, Redis deployment,
Kafka broker, NSQ broker, or other real provider was started by this evidence.

## v1.1.0 maturity boundary

`platform.storage-runtime-v2` remains Planned. Local and S3-compatible object storage
remain Legacy/Blocked. By the maintainer's v1.1.0 scope decision, ObjectStore/Delivery
promotion, RustFS, and the complete Local/S3-compatible conformance matrix are optional
post-v1.1 maturity work. Their absence does not fail the Foundation release and cannot
be converted into an inferred promotion.

The checked-in path `.mss/reports/provider-maturity.json` is intentionally not created
at this checkpoint. A real report must be produced only after selecting one clean
feature-freeze SHA. It must bind the selected v1.1.0 required provider scope to that full
SHA and contain no skipped, failed, zero-run, partial, or cached-only required row before
`mss provider evidence --required --format json` can pass.

## Compatibility, security, and rollback

The CLI and schema are additive and do not change runtime provider APIs or configuration.
Input is confined to the repository, unknown fields fail closed, and output contains only
the fixed evidence fields supplied by the source artifact; release tooling must still keep
secrets, payloads, endpoints, and credentials out of that artifact.

Rollback removes the new root CLI registration and schema together. It does not require a
database migration or provider cleanup because no provider is constructed and no report is
generated by the validator.

## Next release action

After the feature-freeze SHA is selected, generate the required provider maturity artifact
from phase-scoped evidence for that exact commit, then run the validator in required JSON
mode and attach both source and normalized reports to the release evidence. Keep optional
ObjectStore/RustFS rows absent or explicitly non-promoted unless the maintainer elects to run
that separate post-v1.1 work.
