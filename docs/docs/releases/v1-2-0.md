# v1.2.0 发布合同

当前状态：**component-partial / 先由 v1.2.1、v1.2.2 接续，随后由 v1.2.3 完成修复**。
当前稳定版为 [v1.3.2](/releases/v1-3-2)；v1.2.3 仅保留为上一稳定回滚基线。

`mss-boot/v1.2.0` 已从提交 `c0b4b4d7888a67931951f0b40198d98614e979af`
成功发布并完成外部代理解析。`web/antd-v6/v1.2.0` 标签指向同一提交，但发布工作流在
上传包含冒号路由文件名的原始 `dist` 目录时失败，因此没有 V6 构建制品、镜像或
GitHub Release。根 `v1.2.0` 标签从未创建。

所有 v1.2.0 标签和证据保持不可变，不移动、不复用、不补发。以下保留原始范围与门禁
作为审计记录；当时的完整前向修复见 [v1.2.3 发布合同](/releases/v1-2-3)。

原定同步列车要求根仓库、可复用 Framework 和唯一的 Ant Design V6 前端来自同一个
已合并到 `origin/main` 的精确提交：

| 组件 | 版本与标签 | 前置条件 |
| --- | --- | --- |
| Framework | `mss-boot/v1.2.0` | 完整 `GOWORK=off` 测试与 `pre-framework` 授权 |
| Admin V6 | `web/antd-v6/v1.2.0` | 集中前端门禁、精确 SHA 浏览器证据与同提交镜像 |

任何本地运行、topic branch 提交或未合并 PR 的结果都只是预备证据，不能创建标签、
package、镜像或 GitHub Release。历史版本只保留为不可变基线，不参与本轮资格判定。

## 发布范围

### Admin 与前端

- `web/antd-v6` 成为唯一 Admin 浏览器应用、生成目标和发布命名空间；不再提供 V5
  源码、部署路径或浏览器协议兼容层。
- 浏览器使用强制 HttpOnly 会话、CSRF 和一次性 WebSocket ticket；REST Bearer 与 PAT
  只保留给文档化的非浏览器自动化。
- V6 覆盖组织、RBAC、菜单与 API 绑定、日志/任务/通知、在线会话、语言、Option、
  个人资料、凭据自助、主题和 Supplier 生成黄金样例。
- 发布构建维持 900 KiB gzip JavaScript 总预算，并继续验证依赖、审计接受项、单元/
  集成、Chromium E2E、bundle 和同源交付。
- V6 使用 pnpm 10.34.5，文档站使用其独立锁定的 pnpm 9.15.9；发布命令必须显式选择
  对应版本，不能依赖工作站全局 pnpm。

### Framework

- 通用 GORM Delete 的 before/delete 进入同一事务，并使用固定公开错误映射边界。
- 新增基于现有 scrypt 存储格式的常量时间密码校验。
- SecretRef 诊断指纹改为有界 PBKDF2-SHA256 派生，不直接散列环境变量定位符。
- Framework 目标保持源码兼容；若资格检查发现公共可复用 API 不兼容，停止 1.2.0，
  重新进行 SemVer 决策。

## 数据库升级

从现有安装升级时，先备份数据库，再执行全部前向迁移。1.2.0 新增或纳入以下迁移：

- `20260815120000_language_integrity`
- `20260815121000_language_management_permissions`
- `20260815130000_option_integrity`
- `20260815131000_option_management_permissions`
- `20260816120000_hide_example_supplier_menu`
- `20260816163000_account_reauthentication`
- `20260817120000_retire_example_supplier_roles`
- `20260817170000_retire_v5_browser_config`

迁移完成后必须同步实际挂载路由到 API 注册表：

```shell
cd admin
STAGE=local go run . server -a
```

该命令是一次性同步并正常退出，不会长期启动 HTTP 服务。随后再启动后端。仅有
`/healthz` 成功并不足以证明权限数据就绪；还要在“权限管理 → 菜单管理 → 绑定 API”
中确认存在可选 API。空列表视为发布阻塞。

新环境使用其他 stage 或数据库配置时，沿用同一 `server -a` 命令，但必须提供该环境
的非生产测试配置；任何证据中都不得记录 DSN、密码、token 或 cookie。

## 兼容性边界

- 1.2.0 不支持 V5 前端与旧浏览器 token/cookie/WebSocket 协议。升级必须成对部署
  1.2.0 后端与 V6 前端，不能混用旧前端。
- 数据迁移是前向的；旧二进制不保证能读取已升级数据库。
- `admin/go.mod` 在发布提交上必须依赖 `mss-boot v1.2.0`。开发期本地 replace 不能作为
  外部可解析证明。
- `.mss/project.yaml` 与 `.mss/lock.yaml` 保留真实开发快照身份，不因公开版本号人工伪装。
- ObjectStore/RustFS 成熟度仍为独立可选工作，不阻塞 1.2.0，也不会因本次发布自动晋级。

## 资格门禁

结构化入口为 `.mss/features/foundation-v1-2-0-release.yaml`，资格清单只选择该 Feature，
其余已合并 Feature 通过显式 carry-forward 决策保留。

1. 开发检查：严格 doctor、release 工具测试、Feature 校验、三个组件 tag namespace 校验。
2. 功能冻结：根与 Admin Go 测试、Framework `GOWORK=off` 测试、V6 集中门禁、文档构建。
3. 精确 SHA 人工证据：Codex 内置浏览器产品验收和外部 Blueprint 升级演练。
4. `pre-framework`：选择一个成功 readiness run，授权 Framework 与前端写入。
5. 外部解析：在仓库外使用 `GOWORK=off` 解析 `mss-boot@v1.2.0` 并记录 checksum。
6. `pre-root`：选择另一个成功 readiness run，授权根发行版写入。
7. 发布后：核对 tags、Releases、archives、checksums、images、安装、迁移、API 注册表和恢复。

任一实现变更都会产生新的候选提交，并使受影响的旧证据失效。

## 发布顺序

1. 通过 PR 将准备变更合并到 `main`，拉取远端并确认 tracked worktree 干净。
2. 冻结一个完整 SHA，执行 feature-freeze readiness，不授予发布权。
3. 完成同 SHA 浏览器与 Blueprint 证据，解决全部 required blocker。
4. 执行并选择 `pre-framework` 权威 run。
5. 发布 `mss-boot/v1.2.0`，在外部临时模块验证解析与 checksum。
6. 发布同 SHA 的 `web/antd-v6/v1.2.0`、匹配镜像和候选根制品。
7. 执行并选择独立的 `pre-root` 权威 run，再发布 `v1.2.0`。
8. 完成发布后对账后关闭 evidence issue。

禁止移动或复用已发布标签。某组件公开后出现缺陷时，停止后续发布并用更高版本
forward-repair。

## 回滚

发布前必须创建并验证数据库恢复点。部署失败时：

1. 停止继续发布或扩散流量；
2. 恢复升级前数据库备份；
3. 部署上一组已资格化的 V6 后端与前端；
4. 验证登录、菜单、API 绑定、权限负例、会话与核心写入；
5. 保留失败提交、日志摘要和证据链接，修复后选择新 SHA 重跑受影响门禁。

不能通过恢复 V5、移动标签、对生产库执行临时 down migration 或绕过 readiness 来回滚。
