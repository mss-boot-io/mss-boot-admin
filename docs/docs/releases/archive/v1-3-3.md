## 发布顺序

```text
merged main
  -> Framework
  -> Admin
  -> Admin Web candidate / image / GitHub Release
  -> Root tools and Release
  -> Docs
  -> official npmjs
  -> public reconciliation
```

每阶段验证全部前置组件来自同一提交。修复必须通过新 PR；冻结后的变化产生新的候选
提交并重跑受影响阶段。

本次冻结同时纳入 Framework Go、Admin Web、Thin Host、Docs 与 GitHub Actions 的成组
依赖更新。Admin Web 与生成应用统一锁定 Ant Design 6.6.1、Umi Max 4.7.7、Vite 8.2.2
和 Vitest 4.1.11，不能保留旧版本形成双运行时图。

同一源码在升级前后的发布构建分别为 899.96 KiB 和 900.47 KiB gzip JavaScript；因此完整
语料预算从已无余量的 900 KiB 收紧校准为 905 KiB。32 KiB 入口预算和 240 KiB 单异步块
预算保持不变，不能以依赖升级为由绕过发布构建门禁。

## Root 标签晋升权限

Root 标签不能由个人凭据、PAT 或 `GITHUB_TOKEN` 创建。唯一受支持的写入路径是从精确
`main` 提交派发 `root-tag-promotion.yml`，经 `root-promotion` 受保护环境的第二账号审批
后，使用环境 Secret `ROOT_TAG_PROMOTION_SSH_PRIVATE_KEY` 中的专用 Ed25519 私钥，以 SSH
创建一个精确 annotated `v1.3.3` 标签。

仓库必须恰有一个 Deploy Key：标题固定为 `mss-root-tag-promotion`，已验证、已启用且具有
写权限。Root creation ruleset 只允许 `actor_id: null`、`actor_type: DeployKey`、
`bypass_mode: always`；由于该 actor 代表仓库 Deploy Key 这一类别，任何额外 Deploy Key
都会扩大绕过面并阻断发布。不可加入个人、管理员、Integration 或 GitHub App 绕过。

工作流不从网络动态采信主机密钥：它写入并校验 GitHub 公布的 Ed25519 host key 与
SHA-256 指纹，禁用 checkout 凭据和环境中的其他 SSH identity，只推送精确 Root tag
refspec，并在退出时删除临时私钥。Deploy Key 的 tag push 会自然触发唯一的 Root image
与非发布 candidate run；晋升工作流只接受同一标签、完整提交、workflow path、`push`
事件和稳定标题完全一致的证据，不再手动 dispatch 替代 run。

管理员侧治理校验还会通过 repository numeric ID 读取受保护环境的 Secret 元数据，要求
`root-promotion` 恰有一个 Secret 且名称为 `ROOT_TAG_PROMOTION_SSH_PRIVATE_KEY`。校验报告
只记录名称与已配置状态，不能读取或输出 Secret 值。

## 原计划使用方门禁

最终资格从空目录和 Release-built 二进制开始，不允许 Foundation 源码或本地替换：

1. 安装 `mss` 与 `mss-mcp` 并验证版本、提交和摘要；
2. 运行 `mss new app`；
3. 验证 Go Module 在 `GOWORK=off` 下公共解析；
4. 从 npmjs 匿名安装 `@mss-boot-io/admin-web@1.3.3`；
5. 执行 `doctor --strict`、`setup`、`dev` 和 `verify --all`；
6. 验证升级计划、确认应用、第二次 no-op 与业务文件保留；
7. 验证后端、前端和内置浏览器关键流程。

第一次交互式 `mss setup` 使用内置隐藏提示读取初始管理员密码；CI 等非交互环境只在
setup 进程中从密钥存储注入一次性 `MSS_ADMIN_INITIAL_PASSWORD`。该值不得出现在参数、
报告、生成文件或长期服务环境。

## 原计划升级

先安装目标 v1.3.3 工具，确认 `mss --version` 与 `mss-mcp --version` 同源，并备份
代码、配置和数据库。只有保留 `.mss/blueprint-manifest.json` 的 Blueprint Thin Host
才能进行三方升级；手工拼装或丢失基线的仓库要在新目录生成 v1.3.3 基线后迁入业务所有
文件，不能伪造 manifest。

```sh
mss upgrade admin v1.3.3
mss upgrade admin v1.3.3 --apply --yes
mss doctor --strict
mss verify --all
mss upgrade admin v1.3.3
```

第一次计划只读；应用保留业务和未知文件，快照最后写入；最后一次计划必须为空。数据库
变化仍需独立备份、迁移和恢复演练。
