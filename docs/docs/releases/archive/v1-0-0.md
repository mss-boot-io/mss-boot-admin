# v1.0.0 发布合同

> 历史版本：本页仅保留不可变发布、升级与恢复证据，不用于新项目。当前稳定版仍为 v1.3.2；v1.3.5 已永久停止且只保留不可变的部分发布证据；v1.3.6 是尚未发布的候选。当前状态请从 [v1.3.6 候选采用页](/getting-started) 进入。

适用范围：从根版本 `v0.7.0` 升级到已发布的根版本 `v1.0.0`，以及首次从合并仓库发布的 `mss-boot/v1.0.0` 嵌套模块。

:::info
`v1.0.0` 已于 2026-08-09 发布为 stable。根 Release 与先行发布的 Framework Release
均指向 `ee800262c035c5f4242aca1841d077554481d2c4`；精确提交验收记录见
[#471](https://github.com/mss-boot-io/mss-boot-admin/issues/471)。独立
`web/antd/v1.0.0` tag 未发布，不能由根版本状态推导其存在。
:::

## 为什么是首个稳定 1.0

v1.0.0 是 Admin、`mss-boot`、前端、文档和 Agent 工具完成仓库合并后的首个稳定 1.0 边界。它同时增加能力并收紧不安全的历史兼容行为，包含明确的破坏性变化，因此用主版本边界明确下游迁移责任：

- 原根 Admin Go 模块拆分为 Agent 工具根模块、`admin` 应用模块和 `mss-boot` 嵌套模块；
- `mss-boot` 公共模块路径迁移到 `github.com/mss-boot-io/mss-boot-admin/mss-boot`；
- PAT、OAuth、角色授权、默认角色、上传和配置凭据采用更严格的身份与权限合同；
- Admin 运行时动态模型、虚拟 CRUD 和浏览器代码生成被移除；
- 新增数据库迁移和不可由代码回滚重建的安全清理。

因此不能把本版本当作 v0.7.x 的无迁移补丁，也不能把未发布的 v0.8.0 候选版直接改名后沿用其证据。v0.8.0 候选阶段生成的归档、校验和、镜像 digest、工作流结果和冒烟记录都不是 v1.0.0 的发布证据；必须从精确的 v1.0.0 发布提交重新生成并复核。

## 发布范围

| 组件 | 目标标签 | 交付边界 |
| --- | --- | --- |
| Framework | `mss-boot/v1.0.0` | 可在仓库外由 Go module proxy/VCS 解析的嵌套模块 |
| Foundation / Admin | `v1.0.0` | Admin、Agent 工具、合同、文档和经验证的前端制品 |
| Frontend（可选独立发布） | `web/antd/v1.0.0` | 本地与生产用途明确区分的静态制品和镜像 |

根版本依赖 `mss-boot v1.0.0`。本地 `go.work` 会用源码目录替换该依赖，只能证明工作区构建，不能证明下游可下载模块。

## 用户可见变化

- 保留动态菜单，并让菜单、静态路由、页面动作和后端 API 使用同一套当前身份/权限语义；root 继续绕过普通 Casbin 规则，但不能通过通用 CRUD 删除系统不变量。
- PAT 原值只在创建或轮换成功时显示一次，服务端仅保存摘要；旧自动化可能需要重新签发。
- OAuth callback 改为 POST body，state 单次消费，provider token 不进入浏览器存储或用户绑定表；历史 OAuth 账户的本地密码默认关闭，需显式重置后恢复。
- 角色授权与主题配置引入 revision、ETag、`If-Match` 和 `412` 冲突处理，避免管理员之间静默覆盖。
- 配置缓存以数据库 revision 为权威，Redis 故障回退数据库；系统配置仍为 root-only，应用凭据使用独立权限。
- CPU/内存趋势改为后台系统任务采样并返回有界历史，浅色和深色主题均使用主题 token。
- Admin 中的“开发工具”、动态模型、虚拟 CRUD 和浏览器代码生成完全退出产品；仓库级 `cmd/mss` 确定性生成器继续作为开发工具。

分层主题能力虽然已有实现，但在外部 MySQL/PostgreSQL 矩阵和完整浏览器验收完成前保持 `planned/preview`，不能在发布材料中宣称为 stable。

## 稳定发布门禁

以下各项全部为 must：

1. 发布提交来自干净、已评审的 `main`，不存在未审查生成漂移；
2. `go run ./cmd/mss doctor --strict`、`verify --all` 和 `eval run --all` 在精确提交上通过；
3. `mss-boot` 以 `GOWORK=off` 完成 test、race（适用包）和 vet；
4. Admin 在 SQLite、MySQL 8.4 和 PostgreSQL 17 完成 fresh、v0.7 升级、重复迁移和失败回滚矩阵；
5. 完成 PAT/OAuth、最小权限默认角色、角色授权、配置 revision、已移除工具清理的正反向验收；
6. 前端完成 lint、TypeScript、Jest、生产构建、bundle budget、Nginx delivery smoke 和内置浏览器关键路径；
7. 文档构建成功，且上传/部署链路能处理所有生成文件名；
8. 所有正式二进制报告与 tag 一致的版本，静态制品不包含未经批准的 localhost/alpha/beta API 地址；
9. 容器与 GitHub Release 原子协调，Release 记录镜像 digest；
10. 历史内置 OAuth 凭据已在 provider 侧 rotate/revoke，并完成 secret scanner 与安全告警复核；
11. 发布说明列出迁移、破坏性 API、兼容窗口、已知限制、备份和回滚步骤。

任何 must 缺证据时结论都是 NO-GO。

### 人工证据工单

正式发布时传入的 `evidence_url` 必须指向本仓库的独立 issue，并至少记录：

- 候选 tag 与完整 commit SHA、执行环境、执行时间和审批人；
- 仓库外 `GOWORK=off` 解析 `mss-boot/<tag>` 的版本、commit 与测试结果；
- 同一恢复点的数据库、配置、对象存储和制品备份标识，以及隔离恢复演练结果、RTO/RPO；
- 历史 OAuth credential 在 provider 侧 rotate/revoke 的脱敏凭据，以及精确提交的 secret-scanning 结果；
- 二进制版本、ZIP 校验和、前端 endpoint scan、容器 digest/OCI labels 与 no-cache 安装冒烟；
- Release Readiness、v0.7 Upgrade、Theme Database、Docs 工作流的精确提交链接。

说明文档、勾选框或没有候选 SHA 的历史报告都不能替代实际执行证据。工单不得包含 secret、完整 DSN、原始 PAT 或备份下载凭据。

### 构建依赖安全例外

当前 Docs 与 Web 的完整开发依赖图各保留 `image-size` 的两条 high advisory；上游尚无修复版本，且它们不进入生产依赖图。`audit:release` 强制生产 high/critical 为 0，只允许仓库内 `tools/security/pnpm-audit-acceptances.json` 记录的这两条 build-only 例外，并在 **2026-11-08** 自动过期。出现可用补丁、新的 high/critical、作用域变化或超过到期日都会阻断发布，不能把扫描任务执行成功等同于零风险。

## 强制发布顺序

1. 冻结并记录候选提交，生成验证报告与数据库备份/恢复证据；
2. 从该提交创建 `mss-boot/v1.0.0`；
3. 在仓库外创建空临时 Go 模块，并运行：

   ```shell
   GOWORK=off go mod init example.com/mss-release-probe
   GOWORK=off go get github.com/mss-boot-io/mss-boot-admin/mss-boot@v1.0.0
   GOWORK=off go list -m -json github.com/mss-boot-io/mss-boot-admin/mss-boot@v1.0.0
   GOWORK=off go test ./...
   ```

4. 验证解析结果的版本、目录和 commit 与候选一致；失败时停止，不创建根 tag；
5. 在同一提交上重跑根发布门禁；
6. 创建根 `v1.0.0` 后，tag 工作流只生成候选归档与镜像，不自动创建正式 Release；确认精确 SHA 的 Release Readiness、v0.7 Upgrade、Theme Database 与 Docs 工作流全部成功，并把恢复演练、OAuth provider 撤销、secret scan 和审批记录附到仓库 issue 后，才从该 tag 手动运行 `Release`（`publish=true`）公开 stable；
7. 从已发布 tag、ZIP 和容器分别进行禁用缓存的安装冒烟，并记录 digest/校验和；
8. 仅在独立前端合同通过时创建 `web/antd/v1.0.0`。

## `.mss/lock.yaml` 状态规则

`.mss/lock.yaml` 是生成/升级基线，不是发布公告。v1.0.0 发布后它仍保持真实的
`0.1.0/development` 生成基线，因为当前工具尚不能区分 Foundation Release、Blueprint 与
generator 版本并确定性记录发布 commit：

- 没有最终根 tag 和精确发布 commit 时，不写 `1.0.0/stable`；
- 不为尚未发生的升级添加 `upgrades` 记录；
- `blueprint.version` 与 `generatedBy.version` 仅在 Blueprint 和生成器自身真实升版时更新；
- 根 tag 发布后，由确定性生成/升级流程记录真实的 foundation version、commit 和 channel；现有格式没有 commit 时不手工创造未经消费者支持的新字段。
