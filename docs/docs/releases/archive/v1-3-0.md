# v1.3.0 部分发布记录（不可复用）

> 历史版本：本页仅保留不可变发布、升级与恢复证据，不用于新项目。当前稳定版是 v1.3.7；v1.3.5 与 v1.3.6 已永久停止且只保留不可变的部分发布证据。安装、创建或升级从 [v1.3.7 快速开始](/getting-started)进入；Docs 网站可通过 `docs/v*` 独立异步发布，其状态不影响组件、稳定别名或采用。

:::warning
**该列车已停止，不得继续或复用**

Framework <code>mss-boot/v1.3.0</code> 已公开；Admin 发布在独立 Module 元数据门禁失败，
Root、Admin Web、Docs 和 npmjs stable 制品均未完成。已有标签、Release 和失败记录永久

## 1. 原计划发行范围

<code>v1.3.0</code> 原计划成为首个稳定的 Complete Admin Distribution。它把领域中立 Framework、可导入
Admin 应用、完整 React 19 + Ant Design 6 前端、Agent CLI、Thin Host Blueprint、确定性
业务模块生成和升级合同组织为一个协调产品版本。

主要能力：

- <code>admin/app</code> 提供可返回错误、接受 <code>context.Context</code> 的完整应用组合入口；
- <code>admin/business</code> 提供显式的编译期业务模块注册、迁移、权限、菜单、路由和 readiness；
- <code>@mss-boot-io/admin-web</code> 是唯一完整 Admin Web 包，业务页面进入同一 Umi 路由树和
  同一个 <code>dist</code>；
- <code>management-system</code> Blueprint 生成 Thin Host，不复制 Admin、Framework、完整 V6
  源码、Foundation 文档或发布工作流；
- Supplier 是前后端、迁移、权限、菜单、API 绑定、生成、升级和浏览器验收的黄金样例；
- <code>mss spec init --kind module</code> 生成满足当前 V6、导出、权限、E2E marker 与迁移
  身份约束的有效 AdminModule 起点；
- <code>mss upgrade admin</code> 使用三方合并更新受管胶水，保留未知文件和业务自有代码。

## 2. 原计划公开身份

所有协调组件必须解析到同一个精确 merged-main 提交：

| 组件 | stable 身份 | 公开入口 |
| --- | --- | --- |
| Root | <code>v1.3.0</code> | GitHub Release、六个平台 ZIP、Root 容器镜像 |
| Framework | <code>mss-boot/v1.3.0</code> | <code>github.com/mss-boot-io/mss-boot-admin/mss-boot@v1.3.0</code> |
| Admin | <code>admin/v1.3.0</code> | <code>github.com/mss-boot-io/mss-boot-admin/admin@v1.3.0</code> |
| Admin Web | <code>web/antd-v6/v1.3.0</code> | <code>@mss-boot-io/admin-web@1.3.0</code>、前端镜像与 Release |
| Docs | <code>docs/v1.3.0</code> | 独立 Docs Release 与公开站点 <code>release.json</code> |

容器目标：

~~~text
ghcr.io/mss-boot-io/mss-boot-admin:v1.3.0
ghcr.io/mss-boot-io/mss-boot-admin-antd-v6:v1.3.0
~~~

<code>latest</code> 只允许由 stable SemVer 标签推进。任何包含连字符的预发布标签都不得创建或
更新 stable <code>latest</code>。部署应优先固定版本或 digest，而不是依赖可移动别名。

## 3. 工具链和兼容矩阵

| 项目 | v1.3.0 合同 |
| --- | --- |
| Go | <code>1.26.6</code> |
| Node.js | <code>&gt;=24.0.0 &lt;25</code> |
| pnpm | <code>10.34.5</code>（Admin Web/Thin Host）；Docs 独立使用 <code>9.15.9</code> |
| 前端 | React <code>19.2.8</code>、Ant Design <code>6.6.0</code>、Umi Max <code>4.7.5</code> |
| 数据库资格 | SQLite、MySQL、PostgreSQL 的 fresh 与 upgrade 路径 |
| 浏览器应用 | 仅 <code>web/antd-v6</code>；Ant Design 5 已退役 |
| 架构 | 单租户 Admin；后端授权是权威来源 |
| npm Registry | npmjs 默认公开源；GitHub Packages 保留完全相同 tarball 的兼容镜像 |

Admin、Framework 和 Admin Web 的版本核心必须完全一致。禁止把 <code>admin@v1.3.0</code> 与
<code>mss-boot@v1.2.3</code>、预发布前端或本地 <code>replace</code> 组合成生产版本。

## 4. 新项目：推荐 Thin Host

stable 发布完成后，从精确 <code>v1.3.0</code> Foundation checkout 生成项目：

~~~bash
git clone --branch v1.3.0 --depth 1 \
  https://github.com/mss-boot-io/mss-boot-admin.git foundation-v1.3.0
cd foundation-v1.3.0

go run ./cmd/mss new app example-admin \
  --module github.com/example/example-admin \
  --repository example/example-admin \
  --destination ../example-admin \
  --write --format json
~~~

生成结果包含很薄的 Go 入口、业务目录、前端组合配置、<code>.mss/</code> 锁、部署与 CI，不包含
Foundation 核心源码。先审查 JSON 变更清单和生成目录，再提交到新的业务仓库。

手工组合后端时，<code>go.mod</code> 必须精确固定两个公开 Module，且不能提交本地
<code>replace</code>：

~~~go
require (
    github.com/mss-boot-io/mss-boot-admin/admin v1.3.0
    github.com/mss-boot-io/mss-boot-admin/mss-boot v1.3.0
)
~~~

仓库外验证：

~~~bash
GOWORK=off go mod tidy
GOWORK=off go test ./...
GOWORK=off go vet ./...
GOWORK=off go build ./cmd/server
~~~

业务入口通过 <code>admin/app</code> 组合模块，不能导入 Foundation 的 <code>internal</code> 包，
也不能通过包初始化副作用挂载路由或迁移。

## 5. Admin Web 双 Registry 发布与安装

生成项目的 <code>web/.npmrc</code> 默认使用无需认证的 npmjs，并保持精确版本：

~~~ini
registry=https://registry.npmjs.org/
save-exact=true
~~~

默认安装不需要 Registry Token：

~~~bash
cd web
corepack pnpm@10.34.5 install --frozen-lockfile

corepack pnpm@10.34.5 run lint
corepack pnpm@10.34.5 run test
corepack pnpm@10.34.5 run build
~~~

若在已有前端中手工安装：

~~~bash
corepack pnpm@10.34.5 add --save-exact @mss-boot-io/admin-web@1.3.0
~~~

GitHub Packages 保存同一份 tarball 作为兼容镜像；只有明确选择镜像时才临时注入
<code>read:packages</code> Token，且不能写入 <code>.npmrc</code>、lockfile、脚本、日志、截图或报告。
两个 Registry 必须具有完全相同的 version、gitHead、integrity 和 dist-tag。stable 使用
<code>latest</code>，预发布只使用 <code>next</code>。

发布顺序是 Framework、Admin、Admin Web GitHub 镜像与镜像制品、Root、Docs，最后从前端
GitHub Release 取回已校验的同一 tarball 发布到 npmjs。它是最后一次制品发布；之后只允许
只读对账、安装验证，以及首次发布所需的 Trusted Publisher 绑定和临时 Token 撤销，不能再
创建其他 v1.3.0 公共制品。

## 6. 新安装的数据库和 API 注册表

迁移和路由注册是两个显式步骤。只启动页面或看到 <code>/healthz</code> 成功不代表权限数据已就绪。

从源码运行：

~~~bash
cd admin
STAGE=local go run . migrate
STAGE=local go run . server -a
STAGE=local go run . server
~~~

使用 Root Release 中的平台包时，对应命令是：

~~~bash
./admin migrate
./admin server -a
./admin server
~~~

生产环境必须通过已有配置文件、Secret 或环境变量提供实际 Stage 和数据库配置；不要把示例密码
带入生产。带 <code>-a</code> 的一次性命令从完整、已挂载的路由树同步 API 注册表，完成后退出，
不替代常驻服务器。

### API 绑定验收

同步后使用 root 管理权限登录，并执行以下实际验收：

1. 打开“权限管理 → 菜单管理”；
2. 选择任意 <code>MENU</code> 或 <code>COMPONENT</code> 类型节点；
3. 点击“绑定 API”；
4. 确认可选 API 非空，并能看到与当前路由匹配的方法和路径；
5. 保存一个测试绑定，刷新页面确认仍存在；
6. 使用无该权限角色请求对应 API，确认后端拒绝访问。

“绑定 API”为空时，先核对执行 <code>server -a</code> 的二进制版本、Stage、DSN 和常驻服务是否完全
一致；不要通过手工插表或关闭后端授权绕过同步。

## 7. 从 v1.2.3 升级

### 7.1 冻结和备份

在任何写入前记录：

- 当前 Root、Framework、Admin、Admin Web 和 Docs 版本；
- 后端与前端镜像 digest、部署配置和数据库引擎版本；
- 当前 <code>.mss/lock.yaml</code>、Blueprint manifest 和业务提交；
- 当前数据库备份位置、校验和、创建时间和一次实际恢复测试结果。

停止迁移期间的业务写入。使用数据库原生的一致性备份方式（例如 PostgreSQL <code>pg_dump</code>、
MySQL <code>mysqldump</code> 或停写后的 SQLite <code>.backup</code>），并在隔离实例完成恢复演练。
仅有“备份命令成功”而没有可恢复证明，不满足升级门槛。

### 7.2 先生成只读升级计划

在 Thin Host 根目录使用精确 <code>v1.3.0</code> Foundation：

~~~bash
mss upgrade admin v1.3.0 \
  --foundation /path/to/foundation-v1.3.0 \
  --format json
~~~

计划必须明确列出旧/新 Distribution、Go 与 npm 依赖、重新生成项、受管文件、保留文件、
冲突和验证命令。存在冲突时先人工解决，不得直接应用。

### 7.3 显式应用并验证

~~~bash
mss upgrade admin v1.3.0 \
  --foundation /path/to/foundation-v1.3.0 \
  --apply --yes --format json
~~~

升级器只自动修改 Blueprint 管理的 Thin Host 文件，未知文件和业务自有代码保持不变；所有
文件操作与验证成功后才更新基线。随后执行：

~~~bash
GOWORK=off go test ./...
GOWORK=off go vet ./...
GOWORK=off go build ./cmd/server

cd web
corepack pnpm@10.34.5 install --frozen-lockfile
corepack pnpm@10.34.5 run lint
corepack pnpm@10.34.5 run test
corepack pnpm@10.34.5 run build
~~~

### 7.4 迁移、同步、切流

使用新版本二进制在隔离副本验证，然后按顺序：

1. 再次确认可恢复备份和协调制品清单；
2. 运行 <code>admin migrate</code>，失败即停止，不切流；
3. 运行一次 <code>admin server -a</code> 同步实际路由；
4. 启动常驻后端和同版本前端；
5. 验证 readiness、登录、菜单、API 绑定非空、Supplier、核心 CRUD、权限负例、深链接、
   深色主题和控制台健康；
6. 通过后再逐步切换流量并保留观察窗口。

## 8. 数据与行为兼容性

- v1.3.0 迁移是前向迁移；不承诺自动 down migration。
- RC4 暴露的 Core/Business 全局排序问题已改为 Core 后 Business 两阶段执行；修复只重建
  需要的 Supplier 授权投影，不删除 Supplier 业务表或业务数据。
- 历史动态模型元数据表和用户业务表可能为数据保护而保留，但运行时动态模型、虚拟 CRUD
  和浏览器代码生成不会恢复。
- 历史 full-copy Blueprint manifest 会被识别为旧所有权模型，不会被静默重新分类成 Thin
  Host；迁移必须经过冲突可见的计划。
- 浏览器认证使用 HttpOnly Session、签名 CSRF 和一次性 WebSocket ticket；前端隐藏按钮
  不是授权，后端权限始终是权威来源。
- Ant Design 5 不在兼容面内；正式前端只有 <code>web/antd-v6</code>。

## 9. 回滚与恢复

### 发布前

准备缺陷通过新的 Pull Request 修复，合并后选择新的 <code>main</code> 提交并重跑受影响资格门禁。
不得从当前 topic branch 创建 stable 标签。

### 部署后

发生故障时停止扩散和写入：

1. 保存失败版本、提交、制品 digest、数据库状态和脱敏日志；
2. 恢复升级前经过验证的数据库备份；
3. 同时恢复上一组协调的后端、Framework、Admin Web 和镜像，默认基线为 <code>v1.2.3</code>；
4. 恢复对应 Thin Host lock、manifest 和受管文件；
5. 验证登录、菜单、API 绑定、权限负例、关键写入、Session 和 Supplier；
6. 通过新的补丁版本前向修复。

不要在已迁移生产库上临时编写 down migration，不要只回退前端或后端，不要把 V5 当回滚面，
也不要移动 <code>v1.3.0</code> 或任一 RC 标签。

## 10. 标签、制品与不可变性

- Root、Framework、Admin 和 Admin Web 的 stable 标签只能从同一个精确 merged-main 提交创建。
- <code>v1.3.0-rc.1</code> 至 <code>v1.3.0-rc.6</code> 的标签、Release、npm 版本、镜像 digest
  和失败记录永久保留。
- 已公开 stable 标签同样不可移动、覆盖、删除或重新构建成另一内容。
- 任何组件公开后发生故障，都停止后续写入并使用新的补丁版本修复。
- 发布完成必须核对 tag commit、GitHub Release、ZIP 校验和、Go proxy 解析、npm integrity 与
  dist-tag、镜像 digest/架构/SBOM/provenance、Docs <code>release.json</code>。

## 11. 已知限制

- npmjs 是 Admin Web 默认公开安装源，GitHub Packages 是兼容镜像；首次 npmjs 发布需要一次受保护的 bootstrap 身份，随后切换到 npm Trusted Publishing OIDC。
- <code>@ant-design/pro-components</code> 仍固定在经过验证的 v3 预发布版本，因此不能把整个
  前端依赖生态描述为全部 stable。
- SQLite、MySQL、PostgreSQL 是本版本要求的数据库资格范围；其他 GORM 驱动不因能编译就自动
  获得同等发布声明。
- OAuth、邮件、对象存储、消息队列等可选集成需要部署者配置并单独验证。
- 多租户、Ant Design 5、运行时动态模型、虚拟 CRUD、浏览器代码生成、远程业务代码和多前端
  Runtime 均不在产品范围内。
- Docs 独立发布可能晚于四组件 Distribution；公开页面上的版本身份必须通过
  <code>release.json</code> 单独核对。

## 12. 正式完成检查

在把 current stable 从 <code>v1.2.3</code> 更新为 <code>v1.3.0</code> 前，发布管理者必须确认：

- 四个 stable 标签和公开 Release 均指向冻结提交；
- 两个 Go Module 在仓库外、<code>GOWORK=off</code>、无本地 <code>replace</code> 时可解析和构建；
- <code>@mss-boot-io/admin-web@1.3.0</code> 在 npmjs 与 GitHub Packages 的 integrity、gitHead 和 <code>latest</code> dist-tag 一致，下载 tarball 字节相同；
- Root 与前端镜像版本、commit、digest、amd64/arm64、SBOM 和 provenance 正确；
- <code>latest</code> 已从 stable 构建推进，RC6 digest 和引用未改变；
- fresh/upgrade 数据库迁移与 <code>server -a</code> 已证明“绑定 API”非空；
- 外部 Thin Host 的后端、前端、Supplier 和浏览器证据通过；
- Docs stable 页面、公开 <code>release.json</code> 与 <code>docs/v1.3.0</code> 对账完成；
- npmjs 发布发生在全部其他公共写入之后，且官方 Registry 安装、构建与 provenance 对账通过；
- 后续 reconciliation PR 已把机器契约中的 current stable 更新为已发布事实。

任一项缺失都保持 <code>v1.3.0</code> 为 published / evidence-incomplete 或未发布状态，不用人工例外
把失败门禁改成成功。
