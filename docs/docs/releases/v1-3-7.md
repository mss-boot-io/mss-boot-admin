# v1.3.7 发布候选说明

:::warning
v1.3.7 是新的 complete package-first release candidate。候选 Distribution 组件、Root
或镜像即使已经公开，也不等于稳定版；在单独审核的 stable promotion、npm/GitHub Latest
推进及最终 `currentStableVersion` 策略对账完成前，**不可安装、不可创建或升级应用**。
Docs 是异步、非阻断的网站发布面：`docs/v*` 只表示一次网站发布，不决定组件、稳定别名、
current stable 或采用状态。v1.3.2 仍是当前唯一协调稳定版；v1.3.5 与 v1.3.6 都是不可续的
不可变部分发布列车。
:::

v1.3.7 必须从修复 PR 合并后的一个全新、干净、精确 `origin/main` 提交开始。它不移动、
删除、复用或补全任何 v1.3.6 身份。正式 Tag 之前，要用同一提交完成一次非发布 Root
preview，并核对预期制品清单与浏览器验收。

本页描述阶段合同，不以源码文字替代远端发布台账。每次继续操作前都必须重读精确 Tag、
Release、workflow、Go/npm、镜像、Docs `/release.json` 与 mutable alias 身份。

## 候选发布面与稳定别名

| 发布面 | 候选身份 | 阶段合同 |
| --- | --- | --- |
| Framework | `mss-boot/v1.3.7` | preview 后第一个候选 Tag；必须先完成公共模块对账 |
| Admin | `admin/v1.3.7` | Framework 后发布；必须用 `GOWORK=off` 解析公共 Framework |
| Admin Web | `web/antd-v6/v1.3.7` | Admin 后发布；候选 Release tarball 是以后官方 npm 的唯一字节来源 |
| Root | `v1.3.7` | 只发布候选 Root Release，并强制 `Latest=false` |
| Root 与前端镜像 | `v1.3.7` 和精确 commit alias | 候选阶段按不可变 digest 与双架构对账，不推进稳定别名 |
| Docs 网站 | `docs/v1.3.7` 或后续 `+docs.N` | 仅标识网站发布；Root Release 存在后可异步候补，不加入 Distribution 台账，也不阻断稳定推进 |
| 官方 npmjs | `@mss-boot-io/admin-web@1.3.7` | 候选阶段不发布；stable promotion 授权后仅通过 Trusted Publishing/OIDC 首次发布 |
| npmjs `latest` | `@mss-boot-io/admin-web` 的 v1.3.2 | 整个候选阶段保持 v1.3.2；稳定授权后由首次 publish 原子推进 |
| GitHub Latest | Root `v1.3.2` | 整个候选阶段保持 v1.3.2；仅在 npm `latest` 成功后推进 |

这个表是发布阶段合同，不是下载或采用清单。任一 Distribution 公开身份出现前发现缺陷，
可以通过后续 PR 选择新的 merged-main 提交重新 preview；任一 Distribution 身份公开后再
发现需要修改发行源码，则必须停止 v1.3.7，并选择另一个未使用补丁版本。Docs 身份只影响
网站，后续修复沿独立 Docs PR 与 Revision Tag 路径处理，不会停止 v1.3.7 Distribution。

这里的“完整 Distribution 台账”只包括 Root、Framework、Admin、Admin Web、Root/前端
镜像、公共 Go 依赖、校验和、安装器、仓库外 Thin Host、官方 npm 和稳定别名。Docs Tag、
Release、Cloudflare 凭据、部署结果与公开站点不在该依赖图中。Docs 失败只留下“网站部署待办”，
不会停止、回滚或降级已经对账的 Distribution。

候选阶段不得创建 `next`、`candidate`、`release-*` 等临时 npm dist-tag，也不得手工运行
`npm dist-tag`。GitHub Latest 与 npm `latest` 是稳定采用别名，不是候选制品索引。

## 本轮必须修复的两个门禁

### 显式 Root image preview

- `container.yml` 的 `workflow_call` 声明必填布尔 `release_preview`；
- `release.yml` 调用时显式传入 `release_preview: true` 与精确版本；
- 授权、构建信息、多架构构建、OCI 校验、暂存和 artifact 上传全部依赖该输入；
- 合同测试拒绝再用 `github.event_name == 'workflow_call'` 推断被调用模式；
- preview 结束时必须看到并验证 Root image artifact，不能只依赖 workflow 绿色状态。

### 无令牌 npm Trusted Publishing

npm package 的 Trusted Publisher 必须精确配置为：

| 字段 | 值 |
| --- | --- |
| Package | `@mss-boot-io/admin-web` |
| Organization/User | `mss-boot-io` |
| Repository | `mss-boot-admin` |
| Workflow filename | `npm-release.yml` |
| Environment | `npm-auto` |

workflow 保留 `id-token: write`，稳定授权后的唯一发布命令使用
`npm publish --tag latest --provenance`，发布进程继续清除 `NPM_TOKEN` 与
`NODE_AUTH_TOKEN`。Trusted Publisher 的 live 配置必须在第一个正式 Tag 前验证，并在
stable-promotion dispatch 前重新验证；不允许用长期 token、临时 dist-tag 或单独的
`npm dist-tag` 绕过不匹配。

## 资格与发布顺序

1. 修复和候选合同先在 PR Head 完成本地 `mss verify --changed`、影响计划选中的聚焦检查与
   受影响页面的内置浏览器验收，再通过精简后的治理、安全分析、普通 Admin 单测及适用的
   Framework 普通独立单测并合并到 `main`；PR 阶段不再重复完整发布资格套件；
2. 冻结 exact merged-main commit，复查 v1.3.7 远端身份为空；
3. 在该精确提交上只运行一次本地 `make verify-release-evidence COMMIT=<full-sha>`，完成 Go、前端、
   迁移、安全、外部 Thin Host 与回退验收；报告必须绑定完整 SHA，且验证前后
   `trackedCleanBefore`、`trackedCleanAfter` 都为 `true`；
4. 运行一次非发布 Root preview，只构建并核验六平台二进制、前端发布包、SBOM、校验和、
   Root/Frontend 双架构 OCI 及候选 Thin Host 组合，不重复本地质量套件；
5. 核对 npm Trusted Publisher live 身份、GitHub `npm-auto` environment，并确认 npmjs
   `latest` 与 GitHub Latest 都仍精确指向 v1.3.2；
6. 由 `lwnmengjing` 依次创建 Framework、Admin、Admin Web annotated tags，每一步成功
   并对账后才进入下一步；
7. 创建 Root annotated Tag，只触发 Root Release 与 Root image 候选发布；分别对账 Root
   工具、校验和、Root/前端双架构 image，并确认 Root Release `Latest=false`；
8. 通过单独 PR 审核 stable-promotion policy，精确绑定 v1.3.7 和 Root commit，但暂不
   修改 `currentStableVersion`；
9. 从精确 `v1.3.7` Root Tag 手工 dispatch `npm-release.yml`。workflow 先重验完整
    Distribution 台账且明确不读取 Docs Tag 或站点，再用 OIDC 首次执行
    `npm publish --tag latest --provenance`；npm 版本、`gitHead`、
    integrity、provenance 与 `latest` 全部收敛后，才把同一 Root Release 推进为 GitHub Latest；
10. 最后通过另一个 PR 将 stable 从 v1.3.2 对账到 v1.3.7、关闭已消费的 promotion 授权并
    开放采用；该步骤不等待 Docs；
11. 文档团队可在 Root Release 存在后的任意时间候补网站。初始 `docs/v1.3.7` 必须绑定精确
    Root commit；若该 Tag 已存在，则保留不动，并通过单独受审的一次性授权把
    `docsRevisionVersion` 绑定为最低未使用的 `<stable-version>+docs.<N>`、把
    `docsRevisionCommit` 绑定为精确 merged-main 文档源，再创建对应 Revision Tag。Docs 自身仍
    必须核对 Root 祖先、最低修订顺序、受保护部署、Release 资产与校验和、生产
    `/release.json`、首页与嵌套路由、控制台和失败请求；失败时仅保留网站候补待办。

stable-promotion workflow 若中断，只能从同一 Root Tag、版本、commit、actor、workflow 和
已审核 policy 重跑。重跑前必须重建 Framework/Admin/Frontend/Root、Go Proxy、镜像、
候选 tarball、npm package、npm `latest` 与 GitHub Latest 台账；已有 npm 版本只有在
`gitHead`、integrity、provenance 和 alias 全部精确时才可复用，任何冲突都必须 fail closed。
Docs Tag、Release、凭据和站点响应不得出现在该重跑门禁中。

## 安全、迁移与回退边界

- 演示配置仍是编译能力之上的严格 data-only 稀疏覆盖，不能携带脚本、HTML、SQL、URL、
  权限、路由、动态 import 或可执行组件；后端 RBAC 始终是最终权威。
- 数据库迁移保持向前兼容。部署顺序仍是 migrate、一次 `server -a` 同步，再启动长期
  server；普通回退不执行破坏性 down migration。
- 初始化管理员密码只允许隐藏交互输入或单进程 `MSS_ADMIN_INITIAL_PASSWORD`，不得写入
  镜像、配置、日志或发布制品。
- 发布前和发布后的正常回退基线都是完整匹配的 v1.3.2 Admin、Framework、前端、配置与
  冻结锁，并保留可向前兼容的实时数据库。数据库备份恢复只属于有损灾难恢复。

## 完成定义

候选完成要求 Root、Framework、Admin、Admin Web、Root/前端 images、工具、校验和、Go Proxy、
安装器和仓库外 Thin Host 都解析到同一 v1.3.7 与精确 Root commit，且运行时真实浏览器验收
通过；此时它仍不可采用。稳定完成还要求单独受审 policy、OIDC npm publication、npm
`latest`、随后 GitHub Latest 和最终 `currentStableVersion` 全部对账。Docs 网站可在这些步骤
前后独立发布，其完成状态不属于稳定或采用定义。在 Distribution 闭环前，
[v1.3.2 稳定记录](/releases/archive/v1-3-2) 仍是唯一采用基线，
[v1.3.6 记录](/releases/v1-3-6) 仅供不可变审计。
