## 安装与创建

从 [快速开始](/getting-started) 选择平台安装器。安装后先确认两个公共二进制都来自
v1.3.7 Root Release：

```shell
mss --version
mss-mcp --version
```

创建 Thin Host 后，机器可执行项目合同位于 `.mss/project.yaml`，受管 Blueprint 基线记录在
`.mss/blueprint-manifest.json`。人类维护者阅读本站指南；AI Agent 从生成仓库最近的
`AGENTS.md` 开始，再读取 `.mss/**` 与适用 Skills，不把本站叙述当作隐藏指令。

首次初始化没有默认密码。初始用户名为 `admin`，本地 Admin Web 地址为
`http://127.0.0.1:8001`；自动化只允许向一次初始化进程注入
`MSS_ADMIN_INITIAL_PASSWORD`，不得写入参数、日志、生成文件或长期服务环境。

## 升级到 v1.3.7

升级前必须备份代码、配置、数据库和业务数据，确认工作树可恢复，并保留
`.mss/blueprint-manifest.json`。先验证工具与项目健康状态：

```shell
mss --version
mss-mcp --version
mss doctor --strict
```

然后按只读计划、显式应用、最终空计划的顺序执行：

```shell
mss upgrade admin v1.3.7
mss upgrade admin v1.3.7 --apply --yes
mss upgrade admin v1.3.7
mss verify --all
```

第一条命令只生成三方合并计划；逐项解决冲突并确认未知文件与业务自有文件不会被覆盖后，
第二条才写入受管 Thin Host 文件。最后重复同一计划必须无变更，随后完整验证必须通过。

手工拼装或丢失 `.mss/blueprint-manifest.json` 的仓库不能伪造旧 Blueprint 摘要，也不能用
本地 `replace`、源码 checkout 或手写锁掩盖版本。受支持的迁移路径是先生成一个新的
v1.3.7 Thin Host，再按所有权边界迁入规格、配置、数据迁移和业务文件，完成对比与测试后
再切换流量。

## 发布流程为何可复现

v1.3.7 从一个已经合入 `main` 的精确提交冻结，先完成本地完整发布证据和唯一非发布 Root
preview，再按 Framework、Admin、Admin Web、Root 的顺序创建不可变 Tag。Root Tag 触发工具
与镜像发布；官方 npm 只从 Admin Web Release tarball 发布，并在成功后原子推进 npm
`latest` 与 GitHub Latest。最后一个策略 PR 将 current stable 对账到精确发布提交，并关闭已消费
的 stable-promotion 授权。

源修复 PR 先运行 `mss verify --changed` 与受影响的聚焦检查；合并后只在精确、干净的
merged-main 提交上运行完整发布证据：

```shell
make verify-release-evidence COMMIT=77b53d41092741eac62fa6418c0bdbf87413c7cd
```

该入口封装 `mss verify --all --release-evidence --expect-commit <full-sha>`，报告同时绑定完整
提交与验证前后的 tracked-clean 状态。正式 Tag 工作流复用这次验证和 preview 产物，不重复
宽泛质量矩阵。

Root image preview 由调用方显式传入并校验 `release_preview`，不再从 GitHub 事件类型推断。
npm Trusted Publisher 精确绑定组织 `mss-boot-io`、仓库 `mss-boot-admin`、workflow
`npm-release.yml` 与环境 `npm-auto`。这些绑定避免了前序部分列车中“流程绿色但缺制品”或
长期令牌不匹配的常规性失败。

## Docs 网站的非阻断边界

初始 `docs/v1.3.7` 绑定发布提交，保留其不可变历史。若稳定版源文档晚于该 Tag，不能移动或
重用旧 Tag；应在一个独立 PR 中把一次性 Docs 修订授权绑定到最低未使用的
`<stable-version>+docs.<N>` 与精确 merged-main 文档提交，再发布对应
`docs/<stable-version>+docs.<N>`。

Docs 工作流仍需严格校验 Tag、源码、`main` 祖先、合并 PR、Root Release、环境、凭据、
Release 资产、校验和、生产 `/release.json`、首页和嵌套路由，并在内置浏览器检查可见内容、
控制台与失败请求。Docs 失败只形成网站候补待办，不能回滚或降级已经完成的组件发布和稳定
采用状态。

## 安全、迁移与回退

- 页面展示配置只允许编译能力之上的 data-only 稀疏覆盖，不能携带脚本、HTML、SQL、URL、
  权限、路由、动态 import 或可执行组件；后端 RBAC 始终是最终权威。
- 数据库迁移保持向前兼容。部署顺序是 migrate、一次 `server -a` 同步，再启动长期 server；
  普通回退不执行破坏性 down migration。
- 一次性 `MSS_ADMIN_INITIAL_PASSWORD` 不得进入镜像、配置、日志或发布制品。
- 正常回退必须使用完整匹配的 v1.3.7 Admin、Framework、前端、配置与冻结锁；应用回退可
  保留向前兼容的实时数据库，数据库备份恢复仅用于明确评审过的灾难恢复。
- v1.3.5 与 v1.3.6 只能作为不可变审计记录，不能用相邻版本组件拼装回退方案。
