# 权限与组织治理说明

Admin 是单租户管理系统。它把身份验证、角色授权、组织数据范围和业务服务
校验放在后端权威边界中；菜单或按钮是否可见只改善体验，不能代替后端授权。

## 信任边界

一次受保护请求按以下顺序处理：

1. 验证浏览器服务端会话，或验证用户主动创建的 PAT；
2. 从服务端状态加载当前用户和角色，不信任客户端提交的角色声明；
3. 使用 Casbin 对资源类型、路径和 HTTP 方法做精确授权；
4. 对声明了组织数据范围的查询应用后端过滤；
5. 在业务服务和事务中执行输入、状态与并发规则；
6. 记录需要审计的安全或业务变更。

任何一步失败都必须拒绝请求。前端权限列表、路由和组件控制不能绕过这条链路。

## 身份入口

| 调用方 | 凭证 | 额外保护 | 禁止做法 |
| --- | --- | --- | --- |
| Admin Web 浏览器 | 可撤销服务端会话的 HttpOnly Cookie | 可信 Origin、签名双提交 CSRF、会话到期与撤销 | 把 Admin JWT 或长期凭证放入 localStorage |
| 非浏览器自动化 | 用户主动创建并可撤销的 PAT | 后端角色、Casbin 和数据范围仍完整生效 | 把 PAT 当成浏览器会话降级通道 |

登录响应不向 Admin Web 返回可持久化的访问令牌。改密、身份恢复等高风险动作应要求
近期服务端再认证，并按合同撤销其他会话和相关凭证。

## 治理对象

| 对象 | 责任 |
| --- | --- |
| 用户 | 登录身份、状态和组织归属 |
| 角色 | 聚合菜单、API 与组件策略；Root 是显式高权限边界 |
| 部门 | 单租户中的组织树，可参与部门范围过滤 |
| 岗位 | 绑定岗位语义和数据范围 |
| 菜单 | 组织导航与权限元数据，不承担最终授权 |
| API 策略 | 约束后端路径与 HTTP 方法 |
| 组件策略 | 控制页面操作的可见性，必须有对应后端策略 |

角色授权变更应在事务中替换目标角色的精确策略，并通过配置的 Casbin watcher 同步到
其他实例。不要通过重启服务掩盖策略漂移。

## 组织数据范围

当前组织治理可以表达以下常用范围：

| 范围 | 后端含义 |
| --- | --- |
| 全部 | 不添加组织过滤；只授予确实需要全局数据的角色 |
| 当前部门 | 仅匹配当前用户所属部门 |
| 当前及下级部门 | 根据组织树展开当前部门的后代 |
| 自定义部门 | 使用岗位上显式选择的部门集合 |
| 仅本人 | 匹配由当前用户创建或拥有的记录 |

业务实体只有在规格和实现中明确声明对应字段与范围时，才可应用这些过滤。无法证明
归属的数据不得自动推断为可见。新增或修改数据范围必须包含允许、拒绝、无身份和跨范围
测试；仅检查列表页结果不够，还要覆盖详情、导出、更新和删除。

## 业务模块接入

Thin Host 通过结构化 `AdminModule` 规格声明实体、API、权限、菜单、迁移、界面和测试，
再由安装好的 `mss` 确定性生成。一个最小流程是：

```shell
mss spec init inventory --kind module --output .mss/modules/inventory.yaml --write
mss spec validate .mss/modules/inventory.yaml
mss module generate .mss/modules/inventory.yaml
mss module generate .mss/modules/inventory.yaml --write
mss verify --module inventory
```

第一次生成是只读计划。审查后才使用 `--write`。自有后端规则放在 Thin Host 的业务模块
扩展文件中，自有前端规则放在业务扩展目录中；不要复制 Foundation、Admin 或 Admin Web
源码形成第二套安全实现。

每个受保护操作都应具备同一个稳定权限标识，并同时投影到：

- 后端路由和 Casbin 策略；
- 初始角色授权迁移；
- 前端菜单或组件体验；
- 正向和反向授权测试；
- 生成文档与验证报告。

状态变更不得使用 GET。多个写入组成一个业务动作时应使用显式事务；持久化结构变化应
使用前向兼容迁移，并验证全新数据库、历史升级、重复运行和中断恢复。

## Root 与默认角色

Root 绕过必须是后端显式规则，不能由用户名、前端标记或隐藏字段推断。普通角色只拥有
规格声明并经迁移授予的精确策略。创建新业务模块时应遵循最小权限：默认角色只获得完成
职责所需的动作，敏感导出、删除、授权和配置变更单独建权。

## 单租户边界

当前 Admin 合同不提供运行时租户切换、租户列自动过滤或按域名选择租户。组织部门属于同一个
租户内的数据治理结构，不应被解释成租户隔离。若业务需要真正的多租户，应另行设计
身份、数据、密钥、缓存、任务和审计的完整隔离合同，不能只增加一个 `tenant_id` 字段。

## 验证清单

提交治理相关变更前至少确认：

- 无身份、错误角色和越权数据范围都被后端拒绝；
- 允许角色可以完成声明的真实业务流程；
- API 方法和路径与 Casbin 策略完全一致；
- 菜单或按钮隐藏没有成为唯一保护；
- Fresh、upgrade 和重复迁移均通过；
- 会话、PAT、密码和敏感请求体不进入日志或生成报告；
- `mss verify --changed` 通过，合并前按影响运行完整验证。

## 排查顺序

权限问题应先区分身份失败、策略拒绝和数据范围过滤：

1. 确认服务端识别的用户、角色和凭证类型；
2. 确认请求的资源类型、规范化路径和 HTTP 方法；
3. 检查目标角色的精确 Casbin 策略以及 watcher 同步状态；
4. 检查用户部门、岗位和业务实体的归属字段；
5. 用一组允许请求和一组拒绝请求复现，不以页面是否显示按钮作为结论。
