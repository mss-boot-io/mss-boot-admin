## 背景

结合当前仓库实现、已有文档，以及与 HotGo 等开源后台项目的能力对比，可以看到：

- 权限、组织、菜单、日志、任务、代码生成、表单生成，已经是 Go admin 赛道的常见竞争区。
- `mss-boot-admin` 当前已经具备权限治理、组织管理、系统配置、通知任务、国际化、监控统计等较完整的后台基础能力。
- Admin 运行时动态模型、虚拟 CRUD 与浏览器代码生成已于后续实施中移除；仓库级 `cmd/mss` 离线确定性生成器继续作为开发基础设施。

因此，当前阶段更合适的产品策略不是继续扩张功能面，而是先收敛产品主线。

## 当前方向判断

`mss-boot-admin` 后续更适合被定义为：

> 一个面向真实后台系统的 **治理型 + 运营型 + AI 注解协同型 admin 平台**。

这意味着产品重点不再放在“更快生成 CRUD”或“更强低代码”，而是放在：

- 更清晰的权限与组织治理
- 更稳定的系统配置与运营能力
- 更实用的通知、任务、监控、统计能力
- 更适合团队协作的 AI 注解驱动研发流程

## 已退出 Admin 产品的方向

以下运行时能力已从 Admin 产品、API 和菜单中移除：

- 动态模型与虚拟 CRUD
- 浏览器模板/代码生成

升级迁移会清理相应菜单和权限，但不会自动删除历史动态模型元数据表或业务表，
以避免不可逆的数据损失。开发期 `mss module generate` 读取受版本控制的规格并
生成可编译代码，不属于已移除的运行时功能。

## 替代主线是什么

移除 Admin 运行时开发工具之后，平台继续强化以下五个能力支柱。

## 1. 治理核心

围绕后台系统最基础也最长期的能力继续做深：

- 用户、角色、部门、岗位
- 菜单与 API 权限
- PAT、OAuth2、访问边界
- 配置治理与环境隔离

> **架构说明**: 当前为单租户架构，适合单一组织或团队的内部管理系统部署。多租户功能已在产品演进过程中移除。

## 2. 运营能力

围绕后台日常运营与维护场景继续强化：

- 通知公告
- 定时任务
- 监控信息
- 统计查询
- 配置变更与运行态协作

## 3. 集成与扩展能力

保留并强化已经有基础的扩展方向：

- 国际化
- 对象存储/上传
- WebSocket 事件能力
- API-first 的模块扩展方式

## 4. AI 注解驱动研发协作

这里的重点不是“AI 自动生成一切”，而是把 AI 注解用作工程协作契约，例如：

- 设计意图说明
- 接口语义说明
- 约束与边界说明
- 文档与交接输出依据
- 评审与回归时的上下文来源

## 5. 面向生产演进的产品表达

与其强调“低代码”“一键生成”，更适合强调：

- 长期可维护
- 权限治理清晰
- 运维与运营能力完整
- 多角色协作成本低
- AI 参与但不失控

## 一期目标（历史阶段，已完成）

一期先完成了方向统一；随后实施阶段已经完成运行时开发工具下线。

当前阶段的一期目标是：

1. **统一口径**：README、文档首页、功能清单不再把运行时动态模型/浏览器代码生成作为能力。
2. **保留数据**：升级保留历史动态模型数据表，但不恢复已移除的运行时入口。
3. **建立新主线**：对外统一为“治理型 + 运营型 + AI 注解协同型 admin 平台”。
4. **形成后续开发边界**：后续新增能力优先服务新的五个能力支柱；重复工程代码由离线确定性生成器处理。

## 对比 HotGo 等项目时的建议表述

不建议继续从“谁生成更快”来描述差异。

更适合的对比方式是：

- HotGo 等项目偏向 **快速搭建、插件扩展、生成效率**
- `mss-boot-admin` 后续偏向 **治理清晰、运营稳定、长期演进、AI 协同研发**

## 后续阶段边界

方向收口和运行时能力移除已经完成。后续工作依次聚焦：

1. **持续校验文档、菜单、OpenAPI 和权限不存在移除能力漂移**
2. **明确 AI 注解契约与使用规范**
3. **围绕治理与运营能力补强具体模块**
4. **为历史动态模型数据提供显式 Go 模块迁移路径**
