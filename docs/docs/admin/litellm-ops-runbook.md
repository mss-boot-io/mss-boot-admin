# LiteLLM 运营与闲鱼充值手册

本文面向日常运营人员，覆盖用户/Key 管理、闲鱼订单录入、充值、对账与退款复核。系统中的美元额度是运营记账额度，不等同于真实法币支付凭证。

## 1. 每日开始前

1. 登录运营平台，确认“网关总览”显示 LiteLLM 可达、同步时间正常；检查没有待处理的 `approved`、`executing`、`applied_unverified`、`retryable_failed` 或 `reconcile_required` 充值/订单，也没有 `executing` 或 `result_unverified` 管理指令。
2. 在“用户与额度”同步一次，确认待充值邮箱能精确匹配一个 LiteLLM 用户。不要用昵称或买家闲鱼名猜测账户。
3. 在“商品映射”确认“我的闲鱼 → 我发布的”商品 ID 已启用，并核对实付人民币与充值美元额度。这里仅用于找商品 ID，不是成交订单入口。实际商品 ID、店铺和美元额度由运营人员在页面录入，不从商品标题推断，也不写入公共文档。

## 2. 闲鱼成交后的手工流程

“我的闲鱼 → 我发布的”只用于确认商品 ID；成交订单必须在闲鱼 App 的“我的闲鱼 → 我卖出的”核对。闲鱼桌面网页目前无法打开完整“我卖出的”列表。

1. 让买家在订单备注或聊天中提供已经注册 LiteLLM 的邮箱；不要收集密码或 API Key。
2. 在 App 核对订单号、商品、实付金额和“已付款”状态。
3. 在运营平台“闲鱼订单”点击“录入订单”，填写外部订单号、商品/套餐、用户邮箱、实付金额；系统会生成稳定 payload hash 并检查重复。
4. 点击“验证付款”。首期由运营人员确认；未核实付款、邮箱匹配不唯一或商品映射停用时不可继续。
5. 点击“匹配”，选择与订单完全一致的商品/SKU，并让买家邮箱精确匹配唯一一个 LiteLLM 用户；系统会校验店铺、商品、实付金额和映射状态。
6. 点击“批准”，复核匹配用户、实付人民币、将充值的微美元金额及是否联动提高 Key 上限。充值前值、绝对目标和 Key 子步骤要到执行时才会生成，不应在批准阶段猜测。
7. 点击“执行充值”。页面显示 `executing/applied_unverified` 时不要重复新建订单或再次点击直接充值；等待缓存传播后，在原订单上点击“对账回读”。当前没有后台定时对账器。
8. 订单到 `completed` 后，将结果告知买家。若进入 `reconcile_required`，按第 4 节处理。

## 3. 用户、Key 与只读资源运营

- 创建/邀请用户时核对邮箱、角色、默认预算与允许模型；系统明确禁止 LiteLLM 自动附带创建 Key。停用/删除前确认没有进行中的订单。
- 签发或轮换 Key 后，原始 Key 只展示一次。立即通过安全渠道交付给用户；离开弹窗后无法恢复，只能再次轮换。
- 修改 Key 的 TPM/RPM、预算或模型权限时，先说明影响范围。普通新用户的默认策略由部署配置控制，运营端不要批量追溯覆盖存量用户。
- 用户和 Key 的每次写操作都会先创建耐久管理指令，记录脱敏的预期状态和写前摘要，并与充值共用用户租约。上游超时、5xx 或回读不确定时，接口返回待恢复指令；在原指令收敛前，同一用户的新管理写入和充值都会被阻止，不要换入口重试。
- 在“管理指令”中对 `executing/result_unverified` 记录执行“回读对账”。可类型化验证的字段会在权威回读等于预期值时记为 `resolved_applied`；若超过 2 分钟且两次相隔至少 5 秒的权威回读都稳定停留在写前值，记为 `resolved_not_applied`。若值分叉则转人工复核，不会猜测结果。
- Key 签发/轮换的一次性密钥无法自动恢复，部分用户/Key 资料或限额也无法由安全投影完整验证。这类指令只有在未知状态持续至少 2 分钟、连续两次权威观察稳定后，管理员才能凭实际核对结果选择“已生效/未生效”，并必须勾选确认和填写原因；该动作只解除管理隔离，不会重放写入，也不会生成或找回原始 Key。
- 模型页和组织/团队页在本版本均为只读。当前 LiteLLM 模型列表不能可靠给出可管理的启停状态，因此本平台不提供模型启用/停用；组织、成员和团队也不提供创建、修改、分配、删除或充值。对应本地写路由统一返回 `501 operation_disabled`，请从页面链接进入 LiteLLM 原生后台核对和操作。模型凭据、路由和价格配置继续走受控部署流程，不能粘贴到运营页面或日志。

## 4. 充值失败、未知结果与对账

同一用户只能有一笔未决充值。`approved`、`executing`、`applied_unverified`、`retryable_failed`、`reconcile_required` 都会阻止该用户的新充值：用户页直接充值会被拒绝，其他闲鱼订单执行到充值预留时也会被拦截。外部订单仍可留档，但必须先处理原充值记录，不能用新业务单绕过屏障。

- `approved`（直充记录）：充值预留已经落库，但远端写入尚未开始；在用户充值历史中点击“继续原充值”，只续跑这条持久记录。
- `retryable_failed`：远端写入尚未开始或系统已证明未写入；修复原因后，只续跑原订单和原幂等记录。
- `applied_unverified`：写请求结果未知或缓存尚未传播；等待后在原订单点击“对账回读”。
- `reconcile_required`：权威值既不是 before 也不是 target，或其他结果无法安全判断；打开订单核对 before、target_after 和各 Key 子步骤，不能直接重写。
- `terminal_failed`：数据冲突、用户/映射无效或安全校验失败；修正业务数据后另行审核，不强制跳状态。

未知结果第一次及后续早期对账只读 LiteLLM。只有未知状态已持续超过 2 分钟，且两次相隔至少 5 秒的权威回读都稳定等于原 before，执行器才可重发同一个绝对 `target_after`；不得重新计算增量或创建新充值。

当前没有后台定时对账器。运营人员需要等待缓存传播后，在原订单或原充值记录上人工触发恢复操作；连续点击不会绕过 2 分钟屏障或稳定观察条件。

用户页直接充值产生的未决记录也必须操作原记录：`approved` 点击“继续原充值”，其余可恢复状态点击“对账回读”；不能改由闲鱼订单或另一笔直充绕过。充值没有“手工标记完成”或人工强制跳状态接口，只有既有执行器和安全回读能够推进记录。
销售订单关联的充值记录即使出现在用户充值历史中，也只能从原销售订单执行或对账；用户页不会提供恢复按钮，直充创建与对账接口也会拒绝销售订单来源及其 `sales-order:` 幂等命名空间，以保留订单的 claim/CAS/租约屏障。

严禁为了“快速修复”直接修改 LiteLLM 数据库、重复调用加额接口、手工强制完成充值或删除失败单据。若必须人工处理，记录工单/备注和最终 LiteLLM 回读值，但不要把外部工单结论写回成虚假的充值完成态。

## 5. 退款

当前版本的退款动作只要求填写原因，并把订单送入 `refund_review` 人工队列。系统不会自动扣额、批准、拒绝、关闭或冲正。运营人员同时核对原充值单、当前剩余额度和原单之后的消费：

- 未执行充值：在闲鱼侧按业务规则处理退款，并在外部工单记录结果；运营平台订单保持人工复核态。
- 已充值但未消费：记录审批与计划调整；当前版本不能在该退款流程内执行冲正。
- 已部分或全部消费：不要自动扣成负数；按业务规则人工处理，保留审批与说明。

`reversed` 是后续受控冲正能力的预留状态，当前没有进入该状态的 API。不要把“进入退款复核”理解为退款已经完成。

SpendLogs 是只读账目，不得为退款删除或改写历史消费。

## 6. 自动入单的启用条件

当前部署默认没有配置 `LITELLMOPS_CONNECTOR_SHARED_TOKEN` 和 `LITELLMOPS_CONNECTOR_ALLOWED_SOURCES`。导入端点会返回 `connector_disabled`；商品即使设置 `auto_apply=true`，也不会启用自动入单或自动充值。

浏览器登录态不能用作自动化凭据。生产自动入单只允许闲鱼官方开放平台或明确授权 ERP/连接器，并同时满足：

- 独立连接器 token 已存入 Kubernetes Secret，`channel:shop` 已加入来源白名单；
- 请求同时携带 Admin PAT、连接器 token，以及覆盖 Unix 时间戳和原始请求体的 HMAC-SHA256 签名；时间戳偏差不超过 ±5 分钟；
- Admin PAT 对应服务身份至少具备订单核验与匹配权限；命中 `auto_apply` 时还必须具备批准与执行权限。仅有导入权限只允许订单以 `received` 落库，缺少任一后续权限都不会推进或充值；
- 来源被标记为可信，订单状态由可信来源确认“已付款”；
- 外部订单唯一、payload hash 一致；
- 只命中一个启用商品映射和一个 LiteLLM 用户；
- 商品已显式开启 `auto_apply`。

官方接入还需先取得闲鱼准入：订单能力需要申请并获批商家端 B 端 AppKey，淘宝开放平台、闲鱼入驻与合同签约主体一致，并使用签约企业所有的闲鱼账号；处理用户 ID、订单信息的服务部署在聚石塔，通过 OAuth 2.0 获取 access token 后调用 TOP API `alibaba.idle.isv.order.query`。官方快速接入文档说明闲鱼小程序当前仅向定向邀请的服务商开放；未经准入不能把个人闲鱼账号改造成服务端订单源。

- [闲鱼开放平台：小程序快速接入](https://open.goofish.com/doc/quick-start.html)
- [闲鱼开放平台：服务端接入](https://open.goofish.com/doc/development/dev/server.html)

缺少任一系统校验或官方准入条件时只走人工核单，不自动充值。正式启用前用测试店铺/测试用户完成重复回调、超时、退款与回读异常演练。

## 7. 上线、回滚与凭据

1. 上线前备份运营模块数据库，记录当前镜像摘要；先迁移，再滚动启动后端，最后更新前端。
2. 使用不可变镜像标签或摘要，检查 `/healthz`、`/readyz`、网关健康和页面动作权限。
3. 在受保护的数据库克隆或非生产演练环境中，用合成用户和订单重复提交同一业务事件，确认只形成一笔充值；生产上线验收只做健康、只读数据和负向权限检查，不发起真实加额，也不靠事后“清理”冲正。
4. 回滚应用前先判断新状态是否已写入；数据库迁移不可通过覆盖 PVC 回滚。充值单继续保留并对账。
5. LiteLLM master key、连接器密钥、管理员初始密码只存在远端 Secret；不得复制到文档、聊天、构建上下文或日志。
