# Add or change MSS authorization

Backend enforcement is the security contract. Frontend visibility is only its user-experience projection.

## Command and capability context

- A Thin Host uses the installed `mss` v1.3.3 binary.
- A Foundation contributor may substitute `GOWORK=off go run ./cmd/mss` while testing unpublished CLI behavior. Use `mss context --format json` for layout-specific paths.
- The public v1.3.3 generator covers coarse module permissions, backend API/RBAC registration, menu visibility, and generated action checks while `ownership.mode` remains `none`.

Row-level ownership, department scope, tenant scope, state-transition policy, and resource-dependent decisions are not generated by this profile. For those requests, fail closed, create a separate Feature specification, and implement backend filtering/enforcement plus direct-resource and list-query tests in handwritten business code.

## Procedure

1. Identify resource, action, actors, and expected allow/deny behavior. Write a coarse permission matrix.
2. Inspect `.mss/modules/<module>.yaml`, current API routes, generated authorization migration, backend middleware, and frontend access checks.
3. Add or update `spec.permissions` without changing `spec.ownership.mode: none`. Keep permission actions aligned with the module API operations.
4. Validate, inspect, write, and check the projection:

   ```shell
   mss spec validate .mss/modules/<module>.yaml --format json
   mss module generate .mss/modules/<module>.yaml --format json
   mss module generate .mss/modules/<module>.yaml --write
   mss module generate .mss/modules/<module>.yaml --check
   ```

5. Confirm the backend route/action check is authoritative and the menu/action projection uses the same permission code.
6. Add positive and negative tests for every matrix row, including missing identity and a forged direct-resource request where applicable.
7. Run:

   ```shell
   mss verify --module <module>
   ```

## Guardrails

- Default to deny when identity or policy is missing.
- Do not broaden a default role without recording compatibility and security impact.
- Do not claim that frontend hiding enforces authorization.
- Do not represent row scope as generated v1.3.3 behavior.
- Do not record secrets or sensitive request bodies in audit output or tests.

## Output

Include the permission matrix, fully qualified permission codes, backend enforcement location, frontend projection, migration/policy impact, negative tests, and any row-scoped behavior deferred to a separate Feature.
