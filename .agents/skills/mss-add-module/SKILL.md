# Add an MSS management module

Deliver the new capability through the deterministic module contract and generator. Do not hand-build a parallel horizontal CRUD stack.

## Inputs

Collect or infer the minimum complete module definition:

- module name and display names;
- entity fields, types, validation, defaults, indexes, and relations;
- API operations;
- role permissions and default roles;
- ownership or row-level access rules;
- menu parent, path, icon, and order;
- list, form, detail, mobile, import, and export needs;
- status workflow and events;
- test and migration expectations.

When ambiguity remains, choose conservative defaults and record them in the specification rather than scattering assumptions through generated code.

## Procedure

1. Run `$mss-project-onboarding` steps if repository context is not already established.
2. Search `.mss/capabilities.yaml` and `modules/*/module.yaml` for an existing capability or conflicting module name, table, API path, menu path, or permission prefix.
3. Create a specification under `.mss/modules/<module>.yaml` while designing. Use `.mss/modules/example-supplier.yaml` and `.mss/schemas/admin-module.schema.json` as references.
4. Validate immediately:

   ```shell
   go run ./cmd/mss spec validate .mss/modules/<module>.yaml --format json
   ```

5. Dry-run generation and inspect every output path:

   ```shell
   go run ./cmd/mss module generate .mss/modules/<module>.yaml --format json
   ```

6. Confirm that no output escapes the repository, overwrites an unrelated handwritten file, or creates a duplicate route, table, permission, or locale key.
7. Write generated output:

   ```shell
   go run ./cmd/mss module generate .mss/modules/<module>.yaml --write
   ```

8. Commit the specification and generated baseline before implementing custom behavior.
9. Put non-template business rules in handwritten files without a `Code generated by mss` header, for example:
   - `service_custom.go`;
   - `policy_custom.go`;
   - `workflow_custom.go`;
   - focused custom tests.
10. Enforce authorization and row-level rules in backend services or handlers. Frontend visibility is not sufficient.
11. Add or extend tests for:
   - validation and uniqueness;
   - positive and negative authorization;
   - ownership isolation when configured;
   - workflow transition rules;
   - migration from the previous schema;
   - frontend critical paths.
12. Regenerate and prove idempotency:

   ```shell
   go run ./cmd/mss module generate modules/<module>/module.yaml --write
   go run ./cmd/mss module generate modules/<module>/module.yaml --check
   ```

13. Run focused and change-aware validation:

   ```shell
   go test ./modules/<module>/...
   go run ./cmd/mss verify --module <module>
   go run ./cmd/mss verify --changed
   ```

14. Commit test-driven repairs as follow-up commits; do not rewrite already-pushed history.

## Guardrails

- Never use the legacy runtime dynamic-schema subsystem for a new production module.
- Never edit generated files manually when the change belongs in the spec or template.
- Do not silently change an existing table or API path.
- Do not generate destructive migration behavior without an explicit compatibility plan.
- Do not assign permissions only in frontend routes.
- Do not add production secrets, real customer data, or private endpoints to examples or tests.
- Keep generic abstractions out of the module unless at least two real modules require them.

## Completion output

Report:

- specification path and important decisions;
- generated and handwritten files;
- table, API, menu, and permission contracts;
- migration behavior;
- commands actually run and results;
- security and compatibility impact;
- any explicitly deferred non-MVP behavior.
