# Add an MSS management module

Use the deterministic module specification and generator for the capability that v1.3.6 actually implements. Do not turn an unsupported projection into an implied generator promise.

## Command and layout context

- In a generated Thin Host, use the installed `mss` v1.3.6 binary and the paths reported by `mss context --format json`.
- In the Foundation repository, the same examples can be run with the repository entrypoint `GOWORK=off go run ./cmd/mss` while developing unpublished tool changes. Read `.mss/project.yaml`; do not assume Thin Host and Foundation output paths are identical.

## Supported generated profile

The public v1.3.6 profile is intentionally narrow:

- fields are `string`, `enum`, or `bool`;
- ownership is `none`;
- the starter's list/get/create/update/delete/export API, backend RBAC, menu/action projection, Ant Design list/form/detail/export UI, and generated tests are supported;
- relations, import, workflow/state-machine generation, and row-level ownership are not supported by this profile.

If the request needs an unsupported capability, stop before writing generated output. Create a separate Feature specification and implement the behavior in handwritten business-owned code with focused tests. Do not encode a relation, import surface, workflow, or scoped ownership into the module spec and claim it is generated.

## Procedure

1. Read the applicable `AGENTS.md`, `.mss/project.yaml`, `.mss/capabilities.yaml`, and existing `.mss/modules/*.yaml`. Run:

   ```shell
   mss context --format json
   ```

2. Check for collisions in module name, table, API path, menu path, migration IDs, and permission prefix.
3. Create the semantically valid starter at the canonical path:

   ```shell
   mss spec init <name> --kind module \
     --output .mss/modules/<name>.yaml --write
   ```

4. Edit the specification only within the supported generated profile. Keep `spec.ownership.mode: none`.
5. Validate and inspect a read-only generation plan:

   ```shell
   mss spec validate .mss/modules/<name>.yaml --format json
   mss module generate .mss/modules/<name>.yaml --format json
   ```

   Stop if the plan is incomplete, contains an unsupported or deferred projection, escapes the repository, or collides with handwritten files.

6. Write the reviewed output and prove idempotency:

   ```shell
   mss module generate .mss/modules/<name>.yaml --write
   mss module generate .mss/modules/<name>.yaml --check
   ```

7. Put behavior outside the generated profile in handwritten files under the business module layout reported by `mss context`. Backend authorization remains authoritative.
8. Run focused validation, then the changed-file suite when the surrounding change warrants it:

   ```shell
   mss verify --module <name>
   mss verify --changed
   ```

## Guardrails

- Never use the removed runtime dynamic-schema subsystem.
- Never hand-edit a file marked `Code generated by mss`.
- Never silently change an existing table, API path, migration ID, or permission code.
- Do not claim automatic upgrade migration, relation loading, import, workflow, or row-scope behavior that the plan does not project.
- Frontend visibility is not backend authorization.
- Keep credentials, production data, and private endpoints out of specifications and tests.

## Completion output

Report the specification, supported-profile choices, generated and handwritten files, API/menu/permission contracts, migration implications, exact commands and results, and every explicitly deferred capability.
